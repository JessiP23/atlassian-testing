fix: accept scoped Jira tokens, and stop /myself deciding whether we can work

KAN-5 refused at intake with "token rejected" against a token that works
everywhere else. It is a SCOPED token: the site URL answers those with a bare
401 and they only work through https://api.atlassian.com/ex/jira/<cloudId>.
comment_jira.py in this repo already knew that; the Node side did not.

- api() now resolves the cloud id from the public {site}/_edge/tenant_info and
  retries through the api.atlassian.com gateway whenever the site URL answers
  401/403/404, caching whichever base wins. Errors name the base they came from.
- probeIssue judges on READING THE ISSUE, not on /myself. /myself needs the
  read:jira-user scope, which a write-scoped token does not have, so a 401 there
  says nothing about whether the agent can do its job — treating it as fatal is
  what killed the first run.
- the 401 message now lists the causes in order of likelihood and names the site,
  the email and which token kind was tried.
- jiraConfig strips wrapping quotes, trailing newlines, non-breaking and
  zero-width characters (all of which change the Basic header and produce a 401
  that reads as "wrong token"), accepts JIRA_BASE_URL as an alias, and reports
  which values had to be cleaned.
- the workflow probes Jira BEFORE any model runs, so a credential problem costs
  $0 and two seconds instead of a refused run.
- the job-summary step ended on a `for` loop whose last test was false, so a
  successful run showed a failed step: now continue-on-error with an explicit
  exit 0.
- an unreplaced placeholder (PAG_APP_EMAIL=<QA user>) counted as a real login and
  would have had the witness write a sign-in flow that cannot work; placeholders
  now count as absent, in the node and in the spec fixtures.
